Executive summary

PoC Studio is a website where a developer drops in a discovery-meeting transcript (or
audio) and, in under 5 minutes, gets back five deliverables: a requirements brief with
action items, an AI architecture spec with cost estimate, a live sector-specific web
prototype, a GitHub repo with README and CI, and a client pitch deck.

One Orchestrator agent plans each run and hands work to six specialist agents, one per
bottleneck in the problem statement plus a QA reviewer. Two human approval gates (after
requirements, before publishing to GitHub) keep the developer in control without slowing
the run.

Solution architecture

The system has four layers: the website, one orchestrator, six specialist agents, and the
shared tools they call, all on a common data platform.

Meeting-to-PoC Agent Platform -- Technical Solution Proposal

  PoC Studio architecture · 4 layers, 6 agents

  The web app talks only to the orchestrator; agents never call each other directly, so every
  hand-off is logged, validated and resumable from a checkpoint if a step fails.

 End-to-end workflow

  A run goes from transcript to shareable PoC in about 4-5 minutes of agent time, plus
  however long the developer takes at the two gates. Target timings below are design goals
  to validate in the pilot.

    1. Ingest (~10 s). The developer uploads a transcript (.txt, .vtt, .docx) or audio, picks or
       confirms the client sector, and clicks Run. The API stores the file in S3 and creates a
       run record.

                                                                                                                                                                                                                                                    Page 4 of 10
Meeting-to-PoC Agent Platform -- Technical Solution Proposal

2. Extract (~30 s). Meeting Intelligence returns requirements.json : goals, features
   ranked by priority, constraints, budget, sector, and action items with owners.

3. Gate 1 -- confirm scope. The website shows the brief as an editable form. The
   developer fixes anything wrong and approves. This is the cheapest place to catch
   errors.

4. Design (~60 s). Solution Architect writes the spec, diagram and cost table.
5. Build and write, in parallel (~2-3 min).

        Prototype Builder generates the app and loops on build errors until it compiles.
        Pitch and Docs drafts the deck and docs from the spec.
6. Review (~20 s). QA Reviewer checks every output; a failure goes back to the agent
   that owns it, at most twice.
7. Gate 2 -- publish. The developer previews the prototype and deck, then approves
   publishing.
8. Publish (~30 s). Repo and DevOps creates the GitHub repo, pushes code and docs,
   opens issues from action items, and deploys a Vercel preview.
9. Deliver. The run page shows the preview URL, repo URL, deck download and a share
   link for the client.

 Security, guardrails and human-in-the-loop

  Client meetings contain confidential data and the agents write code and push to GitHub,
  so control points are built in from day one.

       Two approval gates. Nothing leaves the platform (repo, deploy, share link) until the
       developer approves Gate 2.
       Sandboxed code. Generated code builds and runs only inside an isolated sandbox
       with no access to platform secrets; network limited to the npm registry.
       Least-privilege GitHub. A GitHub App scoped to one org, repo-create and contents-
       write only; repos default to private.
       Secrets. Keys live in a vault (Doppler, AWS Secrets Manager); a secret scanner blocks
       any push containing keys.
       PII redaction. Optional pass that masks names, emails and phone numbers in
       transcripts before they reach the LLM.
       Data retention. Per-client setting to delete transcripts after N days; LLM providers
       used with zero-retention API terms.
       Cost limits. Per-run token budget and max retry counts; the run stops and asks if a
       budget is hit.
       Audit trail. Every agent step, prompt version, approval and edit is logged for review.

 Implementation roadmap and KPIs

  Build it in four phases of about two weeks each, so a usable tool exists after Phase 1 and
  each phase removes more bottlenecks.

    1. Phase 1 -- Core pipeline (weeks 1-2). Website shell, upload, Orchestrator, Meeting
       Intelligence and Solution Architect agents, Gate 1, live run view. Exit: transcript in,
       approved brief and architecture spec out.

    2. Phase 2 -- Prototype builder (weeks 3-4). Template library for 4 sectors (healthcare,
       logistics, e-commerce, fintech), code sandbox, build-and-fix loop, Vercel preview.
       Exit: 8 of 10 test transcripts produce a prototype that builds.

    3. Phase 3 -- GitHub, deck and QA (weeks 5-6). Repo and DevOps agent, Pitch and
       Docs agent, QA Reviewer, Gate 2, client share page. Exit: full run under 5 minutes of
       agent time.
